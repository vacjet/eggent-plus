# eggent-plus: дорожная карта

Дата: 12.11.2026. Версия: **3** — после проверки на «дрейф в другой продукт».
Основание: `eggent-shortlist.md`, `eggent-requirements-review.md`, решения 12.11.2026.

## Граница продукта

**Eggent-plus = тот же Eggent, но по-русски, с почтой, документами проекта и предсказуемыми расходами.**
Всё, что превращает его в CRM, почтовый клиент, интеграционную платформу, PM-систему или ERP, — не делаем.

Правило, из которого следует всё остальное: **внешние системы — источники данных, а не объекты, которые мы копируем внутрь.**
Клиенты, сделки, остатки, цены живут там, где живут; Eggent их читает по запросу, ссылается на них и не заводит вторую копию.

Готовность к CRM в будущем — это **отсутствие кода**, который мешает: правило выше + запись в `ARCHITECTURE.md`. Когда CRM понадобится, она придёт одним из существующих путей (MCP-сервер, скилл с API, Pi-расширение), а не новым слоем.

## Принципы

1. **Сборка поверх upstream.** `main` — зеркало `eggent-ai/eggent`, `our` — патчи. CI на новый тег накладывает патчи; краснеет — не релизим. Имя: **eggent-plus**, теги `plus-<upstream>-<n>`.
2. **Патч — последнее средство.** Сначала конфиг, скилл, расширение, файл в `data/`. Ядро правим в шести точках: русская локаль, `kb_search` в чате, async-картинки, скриптовые расписания, IMAP-чтение почты, «принять/отклонить».
3. **Проверка умеет падать.** Пункт без негативного теста не сделан.
4. **Макет не трогаем.** Новое встраивается в настройки, панель файлов, карточки доски.
5. **Данные в `data/`**, миграции явные, бэкап и откат обязательны.
6. **Ничего не дублируем из внешних систем.**

## Этап 2 — почта (M)

Только: список писем, открыть письмо, вложения, отправленные агента, статус синхронизации.
**Не делаем:** контакты, метки, папки как в клиенте, ответ из интерфейса, поиск по всему ящику.

| Что | Приёмка |
|---|---|
| Несколько ящиков в `data/`, секреты отдельно, права 600 | три ящика, переключение без перезагрузки |
| IMAP-провайдер рядом с облачным | входящие за 30 дней, тела и вложения открываются |
| Мастер: адрес + пароль приложения → «проверить» | неверный пароль — понятная ошибка |
| Статус: когда обновлялось, успешно ли, что доступно, только чтение | карточка отвечает на все четыре вопроса |

## Этап 3 — секреты и изоляция (L) — **закрыт 13.11.2026 с ограничением**

Первый шаг уже сделан этапом 2: почтовый адаптер с секретом ящика вынесен на отдельный LXC,
доступ агента к Proxmox отозван, `authorized_keys` правится по правилу из `AGENTS.md`.
Осталось: изоляция секретов самого Eggent (терминал агента не должен читать `data/settings` и env),
маскирование в журналах, запрет подмены образа.

Агент сейчас читает `data/settings` и env; каждое подключение добавляет токен.

Приёмка: из терминала агента `data/settings` и env не читаются, работа не ломается; в журналах нет ключей; агент не может подменить образ.

## Этап 4 — чтение из внешних источников (M)

**Проверено 13.11.2026:** пункт «Сайт (sitemap, страницы, robots)» закрывается скиллом + скриптом
без патча ядра; «Директ + Метрика» требует OAuth-токена (api-metrika / api.webmaster v4) — токен
есть в проекте `seo`, значит можно начинать с чтения, а не с разработки.

Не «платформа интеграций», а **два конкретных источника** с честным статусом:

| Источник | Зачем |
|---|---|
| Сайт (sitemap, страницы, robots) | SEO: что проиндексировано, что отдаёт 404 |
| Яндекс.Директ + Метрика | расход, показы, клики, конверсии — для отчётов и гипотез |

Форма реализации: скилл + скрипт (или MCP-сервер, если API удобнее), запуск по расписанию из этапа 1.

Приёмка: сломанный токен даёт «ошибка авторизации»; статус показывает время обновления и доступные объекты; повторный запуск не создаёт дублей.

**Состояние 14.11.2026: закрыт.** Скилл `skills/external-sources/`: сайт (robots, sitemap, коды страниц),
Метрика (счётчики, визиты по месяцам), Вебмастер (сайты, индексация, sitemap), Директ (кампании,
отчёт по дням) — только чтение, без патча ядра. 54 теста на подставном HTTP; живой прогон на рабочем сайте и на токенах Метрики, Вебмастера
и Директа.
Подробности и приёмка — `docs/stage-4-plan.md`.

**CRM, учётные системы, запись — не делаем.** Ждём конкретной задачи; механизм к тому времени будет (скилл/MCP + скриптовое расписание).

## Этап 5 — специалисты и шаблоны (L)

Пакет = `specialist.json` + `SKILL.md` + опционально `.mcp.json` + промпты. Каталог ставится одной кнопкой, в ядро не входит.

Первый набор: **SEO · контекстная реклама · контент · инженер-расчётчик · юрист · документовед.**

Приёмка: каждый специалист проходит свой реальный сценарий; сломанный пакет не ломает приложение.

## Решения по открытым вопросам (12.11.2026)

1. **Справочники — файлы в проекте** (CSV/JSON + индекс `.kb`), отдельного хранилища нет. Появится объём и запросы — тогда и SQLite, а не заранее.
2. **Расходы — счётчики + мягкий порог** с предупреждением в чате. Жёсткой блокировки нет: она превращает помощника в биллинг и обрывает работу на середине.
3. **Провайдера не зашиваем**: ни neuraldeep, ни другой. В базу идёт только универсальный async-адаптер картинок; провайдера и ключ выбирает пользователь.
4. **whisper нужен**: в образе остаётся `whisper.cpp`, `faster-whisper` не добавляем. Задача этапа 1 — доказать, что распознавание работает (модель скачивается, голосовое превращается в текст).
5. **Репозиторий сначала локально**, на GitHub — когда сборка даст первый рабочий релиз.
6. **Русская локаль — этап 0.2, ~1960 строк.** Патча и исходника не сохранилось: в текущем `/app` русских строк нет вообще, тест `grep` по `.next` не нашёл ни одной. Перевод пишется заново по `src/i18n/messages.ts`; это же лучший кандидат в upstream.

## Вывод в трёх строках

Предложение грамотно составлено, но написано **от документации ChatGPT/Work/Codex/LibreChat/Hermes, а не от инвентаризации нашего кода**: из 10 предложенных доработок **3 уже есть в 0.8.0**, ещё 4 есть частично. ## Что действительно полезно (и в каком виде)

1. **Задания-скрипты без модели.** Реальное и дешёвое: наш собственный `check-all.sh` по расписанию в 06:30 — это запуск агента, то есть токены на проверку, которая модели не требует. Плюс журнал запусков и защита от дублей. Берём как есть.
2. **«Принять/отклонить» правку файла.** Диффы и версии уже есть — не хватает именно решения. Это доводит идею Codex до конца и дёшево.
3. **Контракт готовности задачи.** Не новый движок, а поле в карточке доски: что должно получиться, чем проверено, где результат. У нас это уже живёт как соглашение в `AGENTS.md` — его надо сделать механизмом, а не памятью.
4. **Типизированная память: факт / допущение / решение + источник + срок + блокировка.** Самая точная претензия ко всей таблице: у нас в `AGENTS.md` проекта смешаны «решение 10.11.2026» и «факт», и это уже дважды стоило времени. Схема `MemoryEntry` это позволяет — нужны поля и показ.
5. **Разделение «отменить правку файла / отменить внешнее действие / откатить обновление приложения».** В предложении это одна фраза, а мысль правильная и у нас нигде не разделена.

## Что отбросить

- **Интерактивные React-компоненты из ответа модели.** Вложений в это много (схема, рендерер, изоляция, версионирование набора компонентов, тесты), а 80% задачи уже закрывает HTML-страница с превью. Сначала — HTML, генеративный интерфейс потом, если вообще.
- **Отдельный режим исследования.** Субагенты + доска + расписания уже дают план, параллельную работу и отчёт. Нужна только нормальная выдача источников, а не новая поверхность.
- **Изолированные среды разработки (прошивки, веб-проекты).** На 4 ядрах N150 каждая сборка съедает хост; у нас для этого есть отдельные LXC и `git worktree`.
- **Профили как отдельная система настройки.** Опасность: второй набор инструкций рядом с `context.md`/`skills`/`model.json` — рассинхрон гарантирован. Приемлемо только как наследование: профиль — слой, проект — экземпляр.
- **Пункт про «форматы принадлежат Eggent, PI через адаптер».** Про адаптер уже так: `src/lib/engines` (`registry.ts`, `host-types.ts`, `resolve.ts`) — движки подключаются через реестр. Требование версионировать форматы верное, но это гигиена, а не доработка.

## Чего в предложении нет вообще

Ни одной из проблем, которые мы реально ловили:

- `POST /api/chat` падает на вложениях больше ~10 МБ (`bodySizeLimit: "10mb"` в `next.config.mjs`), хотя `/api/files` берёт 100 МБ.
- Карточка вопроса (`eggent_ask_user`) иногда не доезжает — ход висит до перезагрузки страницы.
- Генерация картинок ждёт синхронный ответ `data`/`images` (`src/lib/pi/eggent-tools.ts`), поэтому асинхронный neuraldeep не работает.
- Telegram недоступен из РФ; egress-прокси в Eggent есть (`docker-entrypoint.sh`), нет выходной ноды.
- Семантический индекс проекта (`.kb/`, эмбеддинги) написан, но агенту в обычном чате не выдан.

Для нас это важнее, чем артефакты и профили: первые три пункта — ежедневные, последние два — деньги и нервы.

## Исправленный приоритет

**P0 — надёжность и деньги**
1. Расписания-скрипты без модели + журнал запусков (и перевести наш `check-all.sh` на них).
2. `kb_search` в обычном чате проекта — закрывает «чат по документам» без нового сервиса.
3. Зависание карточки вопроса; лимит 10 МБ на вложения в чате.
4. Картинки через асинхронные API (submit + poll).

**P1 — контроль результата**
5. «Принять/отклонить» правку файла поверх готового диффа.
6. Контракт готовности в карточке доски (требования, проверки, итог).
7. Типизированная память: тип, источник, срок, блокировка записи.

**P2 — удобство**
8. Профили как наследование конфигурации проекта (не дубль).
9. Общий журнал: запуски, проверки, внешние действия.

**Не делаем:** генеративный UI на React, отдельный research mode, изолированные dev-среды.

## Оценка самого документа

| Критерий | Оценка |
|---|---|
| Знание продукта | слабое: половина пунктов уже реализована |
| Знание нашего воркспейса | отсутствует: нет ни одной нашей боли |
| Технические оценки сложности | оптимистичны на 1–2 ступени в 4 из 10 строк |
| Приоритизация | три пункта помечены «1» — приоритета нет |
| Полезное зерно | 5 пунктов из 10, из них 2 — сильные (скриптовые расписания, типизация памяти) |

Как стратегическая записка «куда развивать продукт» — годная. Как план работ для нас — не годится: делать по нему значит переделывать существующее и игнорировать то, что каждый день мешает.
